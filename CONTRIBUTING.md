# Contributing to Chatly

This guide covers everything needed to change Chatly safely: how to set up, how the code fits together, the rules that keep it secure, and step-by-step recipes for the most common changes.

Chatly is a security tool. A small mistake (a wrong capability, a domain added to the allowlist, a secret in a log line) can quietly undo its protection. Read [Rules you must keep](#rules-you-must-keep) before your first change.

## Set up

Install the requirements from the [README](README.md#requirements), then:

```bash
git clone https://github.com/Boldbayar/chatly.git
```

```bash
cd chatly/src-tauri
```

**Unless a step says otherwise, every command in this guide runs in `src-tauri/`.**

```bash
cargo run
```

`cargo run` builds a debug version and opens it. Edits to `ui/` need a restart (quit with ⌘Q, `cargo run` again). There's no hot reload.

> **The debug build uses the same data folder as an installed Chatly** (`~/Library/Application Support/com.chatly.desktop/`). It opens your real vault with your real password. To develop with a clean slate, move the vault aside first and move it back when you're done:
>
> ```bash
> mv ~/Library/Application\ Support/com.chatly.desktop/vault.json ~/chatly-vault-backup.json
> ```
>
> ```bash
> mv ~/chatly-vault-backup.json ~/Library/Application\ Support/com.chatly.desktop/vault.json
> ```

Run the unit tests:

```bash
cargo test
```

If linking fails with an SDK error, see [Troubleshooting](README.md#troubleshooting).

## How Chatly works

### One window, several webviews

```
┌──────────────────────── window "main" ─────────────────────────┐
│┌──────┐┌──────────────────────────────────────────────────────┐│
││shell ││ svc-instagram  (or svc-facebook, svc-telegram; one   ││
││      ││ shown at a time)                                     ││
││      ││                                                      ││
││ ui/  ││ https://www.instagram.com/                           ││
││      ││ private in-memory WebKit store, content.js injected  ││
││ can  ││ can NOT call Rust                                    ││
││ call ││                                                      ││
││ Rust ││                                                      ││
│└──────┘└──────────────────────────────────────────────────────┘│
└────────────────────────────────────────────────────────────────┘
   76 px wide when unlocked; the whole window when locked, on first
   run, or while Settings is open (then the site webviews are hidden)
```

- **`shell`** loads `ui/index.html`. It is the only webview granted any command, through `capabilities/shell.json`.
- **`svc-instagram`**, **`svc-facebook`** and **`svc-telegram`** are created the first time each site is opened (`ensure_webview`), with `.incognito(true)`: a private WebKit store in memory. Nothing they store reaches the disk, except what `save_sessions` encrypts into the vault. They also can't see each other's cookies or storage.
- `layout()` decides what is visible. It always hides the site webviews **before** it grows the shell, so chats never show behind the lock screen.

### State

All state lives in one `Chatly` struct (`main.rs`), shared as `Arc<Chatly>` and reached with `state(&app)`:

| Field | What it holds |
|---|---|
| `vault_path` | Path of `vault.json` |
| `inner: Mutex<Inner>` | `vault` (`None` until a password is set), `locked`, `overlay` (Settings open), `active` site, `open` (sites whose webview exists) |
| `key: Mutex<Option<Key>>` | The vault's data key. `Some` only while unlocked. |
| `last_active` | Last unlock or Chatly prompt. Auto-lock uses the later of this and `guard::last_input()`. |
| `sessions: Mutex<()>` | Serializes webview creation, cookie saving, sign-out and erase |
| `modal: AtomicBool` | One of Chatly's own prompts (Touch ID, link confirmation) has focus. Stops lock-on-hide and lock-on-blur while it's up. |
| `exiting: AtomicBool` | Quit has started |

The UI never keeps state of its own. Rust sends it a `Status` (phase `"setup"`, `"locked"` or `"unlocked"`, active site, settings, Touch ID state, lockout) and `app.js` renders it with `render()`.

### Lifecycle

```
            setup()                     lock_now()
 [setup] ───────────▶ [unlocked] ◀─────────────────▶ [locked]
    ▲                     │      unlock(), unlock_touch_id()
    │                     │
    └──── erase_everything_now() ◀── (from any state)
```

- **Unlock** (`finish_unlock`): stores the key, clears the failure counter, creates the active site's webview, lays out, focuses the site.
- **Lock** (`lock_now`): sets `locked`, pauses media, hides the sites, moves focus to the shell (so typing lands on the lock screen, not in a hidden chat), then on a background thread saves cookies and site storage and drops the key. The key is dropped only if Chatly is still locked when the save finishes.
- **Auto-lock** (`spawn_guard`): a thread that ticks every second while unlocked. Depending on settings, it locks on screen lock or sleep (a gap of more than 20 s between ticks means the Mac slept), and on minimize or hide. It always locks when idle longer than the setting, and saves cookies every 10 minutes. Lock-on-blur isn't here: it's the `WindowEvent::Focused(false)` case in `on_window_event`.

### Cookies and the vault

```
password ──Argon2id──▶ KEK ──unwraps──▶ data key ──XChaCha20-Poly1305──▶ sessions, site storage
                                          │
                     (Touch ID on) ───────┴──▶ login keychain, with a hash of the enrolled fingers
```

- `vault.json` holds: format version, KDF parameters and salt, the wrapped data key, a `key_check` (a known value encrypted with the data key, used to verify a key from the keychain), the encrypted sessions (cookies), the encrypted site storage, and plain settings, lockout counter and last site.
- Each encrypted field uses its own associated data (`chatly/v1/wrapped-key`, `chatly/v1/key-check`, `chatly/v1/sessions`, `chatly/v1/storage`), so one ciphertext can't be swapped in for another.
- Saving (`save_sessions`) reads each open webview's cookies, converts them to `StoredCookie`, encrypts the whole map and writes the file atomically (temp file, mode 600, fsync, rename).
- Restoring (`ensure_webview`) creates the webview on `about:blank`, sets the stored cookies, and only then navigates to the site, so the very first request already carries them.

### Site storage

Some sites keep their sign-in in `localStorage` instead of cookies. Telegram Web stores its auth keys there (`account1`, `user_auth`, `dc`, `dcN_auth_key`), so saving cookies alone would sign you out of Telegram on every launch. A site opts in with `Service::storage_origin()`. Instagram and Facebook return `None` and are unchanged.

- **Saving.** For each open site with a storage origin, `save_sessions` calls `read_site_storage`. It runs `storage::read_script` with `Webview::eval_with_callback` and waits up to 3 s on a channel. The script returns `''` unless `location.origin` is the site's origin, skips items over 32 KiB, and always returns a string primitive (`''+JSON.stringify(…)` inside `try`). That matters: wry `unwrap()`s the conversion of the result, so a non-JSON value would crash Chatly. `storage::parse` decodes the result twice (a JSON string, then a string-to-string map) and enforces the caps again in Rust: 32 KiB per item and 512 KiB in all, kept in key order. If anything fails (timeout, wrong origin, bad JSON), the copy already in the vault is kept.
- **Storing.** `vault.storage` is a separate sealed field (`Storage`: site id → key → value) with its own associated data. "Stay signed in" off, sign-out and erase clear it together with the cookies (`Vault::forget_sessions`, `sign_out`).
- **Restoring.** `ensure_webview` reads the site's saved items and adds `storage::restore_script` as a main-frame `initialization_script`, so it runs before the page's own scripts on every load. It does nothing unless `location.origin` matches. On the first load it sets the `sessionStorage` marker `chatly-restored`, and writes the items only if `localStorage` is still empty. The marker stops it from writing a signed-out session back after the user logs out inside the site and the page reloads. The data is embedded as `JSON.parse("…")`, built with `serde_json`, never by string concatenation.

### Links

- Each site has two domain lists in `services.rs`. `domains()` may load inside its webview. `link_domains()` is a superset whose links the page handles itself. Instagram and Facebook both use `META_DOMAINS` for both. Telegram loads only `web.telegram.org`, but leaves `t.me`, `telegram.me` and `telegram.dog` links to Telegram Web, which opens them inside Telegram.
- `content.js` catches clicks on links outside `link_domains()` and turns them into `window.open`. `Service::content_script()` fills its `__CHATLY_LINK_DOMAINS__` placeholder with the site's list, as JSON.
- `on_new_window` → `open_popup`: Meta's redirect links (`l.instagram.com`, `l.facebook.com`, …) are unwrapped. URLs the site owns (`Service::owns`) load in place. Other `http(s)` URLs go to `open_in_browser`, which strips tracking parameters, asks (if `confirm_links` is on), and runs `/usr/bin/open`.
- `on_navigation` → `services::allowed_in_app(svc, url)` blocks everything else from loading in that site's webview, including in iframes. A `blob:` URL must belong to the same site. Captcha frames are allowed for every site.

## Rules you must keep

Each rule exists because breaking it causes a real security or reliability bug.

**Isolation**

1. **Only the `shell` webview may call Rust.** Never add a site webview label, a remote URL or `"remote"` to any capability. Never set `withGlobalTauri` to `true`. The self-test checks that instagram.com can't call anything.
2. **Every command is listed in three places**: `generate_handler!` in `main.rs`, `COMMANDS` in `build.rs`, and `allow-…` in `capabilities/shell.json`. Listing it in `build.rs` makes Tauri deny it unless a capability grants it. Never skip `build.rs`.
3. **Never pass page-controlled text into `call_shell` or `eval`.** The shell is privileged. Build arguments with `serde_json::to_string` or use numbers and `&'static str`. `badge()` only ever receives a number parsed from the page title, never the title itself.
4. **Domains live only in `services.rs`.** `content.js` gets its list from `Service::content_script()`. Never hard-code a domain in `content.js`, and keep every `domains()` entry in `link_domains()` too (the `link_domains_cover_domains` test checks this).
5. **`allowed_in_app` must stay silent.** It runs for every frame, not just clicks, so it can't tell a link the user clicked from an embedded iframe. Return `false`; never show a dialog from it.
6. **Only `http` and `https` reach `/usr/bin/open`.** `open` would launch apps for other URL schemes. Keep the check in `launch_browser`.

**Secrets**

7. **Wrap passwords and keys in `Zeroizing`** as soon as they arrive (see `setup`, `unlock`, `change_password`).
8. **Never log secrets.** No passwords, keys, cookie values or cookie names in `eprintln!`. Debug-only diagnostics go behind `#[cfg(debug_assertions)]`.
9. **Nothing unencrypted goes to disk** except the settings, counters and last site already in `vault.json`. No caches, no logs, no WebKit persistent stores. Site storage goes only into the sealed `storage` field.

**Concurrency**

10. **Lock order: `sessions`, then `key`, then `inner`.** Take only the ones you need, but never in a different order, or two threads can deadlock. Don't call a function that locks `key` while you hold `inner`.
11. **Never wait on the main thread from the main thread.** `save_sessions`, `ensure_webview`, `select` and anything that reads webview cookies wait for the main thread. Menu handlers, window events and plain (non-`async`) `#[tauri::command]` functions all run **on** the main thread. Call these from an `async fn` command, or move them to a thread with `std::thread::spawn` (see `on_menu` and `lock_now`).
12. **Slow work goes through `blocking()`.** That includes Argon2id (about ⅓ s), the Touch ID prompt and the network check, so they don't stall the async runtime.

**Locking**

13. **Hide before you show.** Any new view mode must hide the site webviews before the shell grows. Add it to `layout()` instead of showing or hiding webviews elsewhere.
14. **Re-check `locked` after anything that waits.** A dialog callback, a thread or an `await` can finish after Chatly has locked. See `open_in_browser`'s dialog callback.
15. **Set `modal` around Chatly's own prompts.** Otherwise the prompt taking focus triggers lock-on-blur.
16. **Commands that need the vault open start with `require_unlocked(&app)?`.**

**Cookies**

17. **Keep the cookie domain quirk.** `StoredCookie` stores the domain without a leading dot. `to_cookie()` writes it as `..instagram.com` because wry strips one leading dot before handing it to WebKit, and WebKit treats a dot-less domain as host-only. The `cookie_domain_keeps_its_dot` test guards this.

**Site storage**

18. **Treat site storage as page-controlled and secret.** Read it only with `read_site_storage`, from off the main thread (rule 11), and only through `storage::parse`, which caps its size. The read script must check the origin and always return a string. Never log storage keys or values (counts only, debug builds only), never pass them to `call_shell`, and restore them only with `storage::restore_script`.

## Recipes

Every recipe ends with **verify**. Do that step, and include it in your pull request description.

### Add a command the UI can call

Example: an `app_version` command that returns Chatly's version.

1. **Write the function** in `src-tauri/src/main.rs`, in the commands section (after `security_check` is a good spot):

   ```rust
   #[tauri::command]
   fn app_version() -> &'static str {
       env!("CARGO_PKG_VERSION")
   }
   ```

   Patterns to copy:

   | Need | Do |
   |---|---|
   | Only allowed while unlocked | First line: `let st = require_unlocked(&app)?;` and take `app: AppHandle` as the first argument |
   | Can fail | Return `Res<T>` (`Result<T, String>`). The `String` is shown to the user, so write a plain sentence: `"Touch ID is turned off."` |
   | Slow, or touches webviews or cookies | Make it `async fn` and run slow parts with `blocking(move \|\| …).await?` (rules 11 and 12) |
   | Takes a password | `let password = Zeroizing::new(password);` on the first line (rule 7) |
   | Changes what the UI shows | Return `Ok(status_of(&app))` and `render()` the result in JS, or call `push_state(&app)` |
   | Returns data | The return type must derive `Serialize`. Add `#[serde(rename_all = "camelCase")]` so JS sees camelCase fields. |

2. **Register it** in `main()`, in `tauri::generate_handler![ … ]`:

   ```rust
       security_check,
       app_version,
   ])
   ```

3. **Declare it** in `src-tauri/build.rs`, in `COMMANDS`:

   ```rust
       "security_check",
       "app_version",
   ];
   ```

4. **Grant it to the shell** in `src-tauri/capabilities/shell.json`. The permission is `allow-` plus the command name with `_` replaced by `-`:

   ```json
       "allow-security-check",
       "allow-app-version"
   ```

5. **Call it** from `ui/app.js`:

   ```js
   const version = await invoke('app_version');
   ```

   Arguments are passed as an object, with **camelCase** keys for **snake_case** Rust parameters. For `fn sign_out(app: AppHandle, service: Service)`, JS sends `invoke('sign_out', { service: 'instagram' })`. A parameter `new_name: String` would be `{ newName: '…' }`.

6. **Build**: `cargo run`. `build.rs` creates `permissions/autogenerated/app_version.toml`. Commit it.

**Verify**: the call works from the UI. If it fails with an error mentioning "not allowed", you missed step 3 or 4.

### Push something from Rust to the UI

The UI exposes `window.chatly` with `update(status)` and `badge(service, count)`. To add another:

1. In `ui/app.js`, add a method to the `window.chatly` object:

   ```js
   window.chatly = {
     update: render,
     badge(service, count) { … },
     notice(text) {
       setText('#some-element', text);
     },
   };
   ```

2. In Rust, call it through `call_shell`, building the arguments with `serde_json` (rule 3):

   ```rust
   let arg = serde_json::to_string("Saved.").unwrap_or_else(|_| "null".into());
   call_shell(&app, &format!("notice({arg})"));
   ```

**Verify**: the message appears. Then try a string containing `'`, `"`, `\` and `</script>`. It must appear as text, not break anything.

### Add a setting

Example: a checkbox `pause_on_switch`.

1. **Add the field** to `Settings` in `src-tauri/src/vault.rs`:

   ```rust
   pub struct Settings {
       …
       pub wipe_after_failures: bool,
       pub pause_on_switch: bool,
   }
   ```

2. **Give it a default** in `impl Default for Settings`:

   ```rust
           wipe_after_failures: false,
           pause_on_switch: false,
   ```

   Existing vaults don't have the field. `#[serde(default)]` on `Settings` fills it from `Default` when they load, so no migration is needed.

3. **Validate it** in `Settings::sanitized()` if it's a number. Values from the UI are never trusted:

   ```rust
   self.auto_lock_minutes = self.auto_lock_minutes.clamp(1, 60);
   ```

4. **Add the control** to `ui/index.html`, inside the right `<div class="card">` in Settings. `data-setting` is the field name in **camelCase**:

   ```html
   <div class="row">
     <div class="row-text">
       <label for="s-pause">Pause videos when switching sites</label>
       <p>One short sentence on what it does.</p>
     </div>
     <input id="s-pause" class="switch" type="checkbox" data-setting="pauseOnSwitch">
   </div>
   ```

   `app.js` loads and saves every `[data-setting]` element automatically. A checkbox sends a boolean. A `<select>` sends `Number(value)`, so its option values must be numbers (see `#s-minutes`). Text settings need a change to `saveSettings()` in `app.js`.

5. **Use it in Rust.** Read it under the `inner` lock:

   ```rust
   let pause = state(&app).inner().vault.as_ref().is_some_and(|v| v.settings.pause_on_switch);
   ```

   Inside the auto-lock loop, use the copy `s` (`s.pause_on_switch`). If the setting changes something about the window right away (like `hide_from_capture`), apply it in `update_settings` and also in `main()` at startup.

6. **Document it** in the Settings table in `README.md`, including the default.

**Verify**: toggle it, quit with ⌘Q, reopen and unlock. The setting kept its value. Also start with a vault created before your change: it loads, and the setting has its default.

### Add a menu item or keyboard shortcut

1. **Add the item** in `build_menu` (`main.rs`) to the right submenu. The id is a prefix plus a name:

   ```rust
       .item(&item("nav:messages", "Messages", "CmdOrCtrl+Shift+M")?)
       .item(&item("nav:notifications", "Notifications", "CmdOrCtrl+Shift+N")?)
   ```

   Accelerators use `CmdOrCtrl`, `Shift`, `Alt` and a key, joined by `+`. Check that the shortcut isn't already used in `build_menu`, and that it isn't a standard macOS shortcut.

2. **Handle it** in `on_menu`. It runs on the main thread, so anything other than `lock` goes inside the existing `std::thread::spawn` (rule 11). `nav:` ids are passed to `navigate_active`, so add a case there:

   ```rust
       "messages" => wv.navigate(active.messages()),
       "notifications" => wv.navigate(active.notifications()),
   ```

   and add `notifications()` next to `messages()` in `services.rs`, with one URL per site.

3. **Document it** in the shortcuts table in `README.md`.

**Verify**: the shortcut works while unlocked, and does nothing while locked or on first launch (`navigate_active` returns early).

### Allow a new domain inside Chatly

Only do this when a site's page breaks because a domain it needs is blocked. With `cargo run`, blocked navigations print `chatly: blocked a frame navigation to …` in the terminal.

1. Add the registrable domain (no `www.`, no scheme) to that site's list in `src-tauri/src/services.rs`: `META_DOMAINS` for Instagram and Facebook, `TELEGRAM_DOMAINS` for Telegram. Subdomains are included automatically. Add it to the site's link list too (`TELEGRAM_LINK_DOMAINS`; the Meta sites use one list for both). `content.js` picks it up on its own (rule 4).
2. If the site only needs it inside frames for login challenges, add it to `CAPTCHA_DOMAINS` instead. That list is allowed for every site.
3. If the site only needs its links handled by the page (like Telegram's `t.me`), add it to the link list alone, not to the site's domains.
4. Add tests in `services.rs`, under `meta_hosts`, `telegram_hosts` or `in_app_rules`: one URL that must pass, and lookalikes that must fail (`https://newdomain.com.evil.example/`, `https://notnewdomain.com/`). If the domain belongs to one site, check in `sites_stay_apart` that the other sites still refuse it.

**Never allow** a domain where anyone can host pages (for example `*.github.io`, `*.googleusercontent.com`, `*.cloudfront.net`), and never allow plain `http`.

**Verify**: `cargo test`, and the broken page works.

### Add a site

Example: adding Threads. Telegram was added this way, so its code is a complete example. Do the steps in order. The compiler flags most places you miss, because every `match` on `Service` must cover the new variant.

1. **`src-tauri/src/services.rs`**
   - Add the variant: `Threads,` to `enum Service`. Its serialized id is the variant name in lowercase (`"threads"`).
   - Add it to `ALL`, and change the array length: `pub const ALL: [Service; 4] = [Service::Instagram, Service::Facebook, Service::Telegram, Service::Threads];`
   - `id()`: `Service::Threads => "threads",`. This must equal the lowercase variant name, because the UI, the menu ids and the saved sessions all use it.
   - `label()`: `Service::Threads => "svc-threads",`
   - `home()` and `messages()`: the site's URLs. If the site has no messages page, return its home.
   - `domains()` and `link_domains()`: the domains the site may load inside Chatly, and the ones whose links its own page handles ([previous recipe](#allow-a-new-domain-inside-chatly)). Threads is Meta's, so it can return `META_DOMAINS` for both. A site from another company gets its own lists, like `TELEGRAM_DOMAINS`. Never add another company's domain to `META_DOMAINS`. Open the site in a normal browser with the developer tools' Network tab to see which domains it loads pages and frames from.
   - `storage_origin()`: `None` if the site keeps its sign-in in cookies. If it keeps it in `localStorage` (check the Application tab of the developer tools after signing in, then delete the cookies and reload), return its origin, such as `Some("https://www.threads.net")`. See [Site storage](#site-storage).
   - `unread_in_title()`: `true` only if the page title starts with the unread count, as in `(3) Instagram`.
   - If the site wraps outbound links in a redirect, add its host to `unwrap_link_shim`.
2. **`src-tauri/src/main.rs`**, in `build_menu`, View submenu: `.item(&item("svc:threads", "Threads", "CmdOrCtrl+4")?)`. `on_menu` handles `svc:` ids already.
3. **`ui/index.html`**
   - An icon in the `<defs>` sprite sheet. Draw your own simple 24×24 line icon: don't copy the site's logo, which is a trademark.

     ```html

   - A rail button after the Telegram one. `data-service` is the id:

     ```

   - A sign-out row in the Accounts card:

     ```html

     </div>
     ```

   `app.js` wires up `.svc` and `[data-signout]` buttons on its own. Selecting, badges, sign-out and saved sessions all work from the id.
4. **Optional**: add the site's host to the list in `netcheck::run` so the Work laptop check tests its certificate too.
5. **Docs**: update the README (title line, rail table, shortcuts, limits) and the disclaimer if the site belongs to another company.

A new variant is also a vault format change in one direction: Chatly versions from before the new site was added don't know the new id. Since this release, `Vault::load` reads an unknown `last_service` as Instagram (`known_service`). Older builds don't, and set the vault aside as damaged when its last site is one they don't know. Say so in the release notes.

**Verify**: sign in to the new site, lock, unlock: still signed in. Quit and reopen: still signed in. Sign out from Settings: signed out, other sites unaffected. `cargo test` passes.

### Add a Work laptop check

1. In `src-tauri/src/netcheck.rs`, write a function returning a `Finding`:

   ```rust
   fn firewall() -> Finding {
       let label = "Firewall".to_string();
       let Ok(output) = Command::new("/usr/libexec/ApplicationFirewall/socketfilterfw")
           .arg("--getglobalstate")
           .output()
       else {
           return Finding { label, level: "info", detail: "Couldn't read the firewall state.".into() };
       };
       …
   }
   ```

   - `level` is `"ok"`, `"warn"` or `"info"` (couldn't tell). The UI colors it.
   - `detail` is shown to the user. Say what it means for their chats, in one or two sentences.
   - Always call programs by absolute path. Give anything that touches the network a timeout.
2. Add it to `run()`: `let mut out = vec![mdm(), proxy(), firewall()];`

**Verify**: run **Settings → Work laptop check**. The new line appears, with the right level, on a Mac where the condition is true and on one where it's false.

### Change the vault format

`vault.json` from older versions must keep working.

- **Adding a plain field** (like a setting): add it with `#[serde(default)]`. Nothing else is needed.
- **Never change** what an existing field means, or its encoding.
- **Changing the crypto** (algorithm, KDF parameters, what is encrypted together):
  1. Bump `FORMAT_VERSION` in `vault.rs` and use new AAD strings (`chatly/v2/…`).
  2. `Vault::load` doesn't check `version` today. Add the check, and convert old vaults on the first unlock (when the password and key are available), then `persist`.
  3. Add a test that loads a v1 `vault.json` written by the current code, unlocks it, and reads its sessions.
- KDF parameters are stored per vault, so making Argon2id stronger only needs new constants. Existing vaults get them on the next password change (`rewrap` calls `Kdf::fresh()`).

**Verify**: `cargo test`. Then manually: create a vault with the old build, open it with the new one, and check you're still signed in.

### Change the UI

- No build step and no npm. Edit `ui/`, quit Chatly, then `cargo run` again (Cargo rebuilds when `ui/` changes).
- The CSP in `tauri.conf.json` applies. Scripts and styles only from files in `ui/`: no inline `<script>`, no `style="…"` attributes, no `<style>` blocks. Images only from `ui/` or `data:` URLs. No remote fonts or CDNs. No `fetch` except to Tauri itself.
- Build DOM with `createElement` and `textContent`. Don't use `innerHTML` with anything that came from Rust or a page.
- Never keep passwords in variables longer than the `invoke` call. Clear the field afterwards (see `resetLock`).
- Every screen is a `<main>` or `<section>` shown and hidden by `render()` from the `phase` in `Status`. Add new screens the same way, not with separate state in JS.
- Keep it keyboard-accessible: real `<button>`s and `<label for>`, `aria-expanded` on toggles, and `focusSoon()` the first field when a screen opens.

**Verify**: light and dark mode, the smallest window (760×540), and keyboard-only use (Tab, Return, Esc).

## Testing

### Unit tests

```bash
cargo test
```

| Area | Tests |
|---|---|
| `vault.rs` | Password round trip and rejection, the KDF parameters, a fresh salt, key and nonce every time, sessions and site storage encrypted and bound to the key, tampering detected, encrypted fields can't be swapped (sessions and storage included), damaged fields are errors and not crashes, password change keeps data, lockout timing, settings defaults and clamping, older vaults and unknown last sites still load, the vault file is mode 600 and loads back, cookie expiry and attributes, cookie domain dot |
| `services.rs` | Site ids and labels, Meta and Telegram hosts and lookalikes, the in-app allowlist per site, sites can't load each other, captcha hosts, special URL schemes, link domains cover domains, link unwrapping, tracking removal, and rule 4 (each site's `content.js` gets exactly its `link_domains()`, and the file hard-codes none) |
| `storage.rs` | Parsing what the read script returns, unusable results, per-item and total caps, origin checks, values with quotes, backslashes and `</script>` survive the restore script |
| `main.rs` | Unread count parsing, duration text, password length in characters, rule 1 (only the local shell has a capability, `withGlobalTauri` is off, the CSP is strict) and rule 2 (every command is in `build.rs`, `generate_handler!` and `shell.json`) |
| `netcheck.rs` | Certificate errors count as interception, network errors don't |
| `guard.rs` | Screen-lock state is readable. **Fails if run while the screen is locked or over SSH.** CI skips it. |

**Every change in behavior comes with a unit test**, added before you commit: a new function, domain, setting, parser or command, and every bug fix (with a test that fails without the fix). Put it in the `#[cfg(test)] mod tests` of the module you changed. Only changes with no effect on behavior, such as documentation or formatting, are exempt. If a rule test fails, fix the code: never weaken, `#[ignore]` or delete a test to get a change through. [AGENTS.md](AGENTS.md) gives coding agents the same rule.

### End-to-end self-test

```bash
CHATLY_SELFTEST=1 cargo run
```

Debug builds only. It takes about 3 minutes and needs internet access to instagram.com, facebook.com and web.telegram.org. It signs in to nothing. The window appears and minimizes by itself, so don't use the Mac while it runs. It checks setup, Instagram loading, blocked navigation, IPC refusal from instagram.com, lock and unlock, that the vault contains no readable cookies, session restore, store isolation between sites, Telegram loading and staying on its own domain, Telegram's local storage saved encrypted and restored into a new webview, minimize-to-lock, idle auto-lock and erase. Output lines start with `[selftest] PASS` or `FAIL`. The exit code is 0 only if everything passed.

It **refuses to run if a vault already exists** and erases what it created. On a Mac where you use Chatly, move your vault aside first ([Set up](#set-up)).

### Continuous integration

Every pull request to `main`, and every push to it, runs [`.github/workflows/ci.yml`](.github/workflows/ci.yml):

| Job | Runner | Checks |
|---|---|---|
| Format and syntax | Ubuntu | `cargo fmt --all -- --check`, `node --check` on `ui/app.js` and `src-tauri/src/content.js`, JSON syntax of `tauri.conf.json` and `capabilities/` |
| Clippy, tests and build (macOS) | macOS | `cargo clippy --locked --all-targets --all-features -- -D warnings`, `cargo test --locked --all-features`, `cargo build --locked`, then fails if the build or `scripts/third_party_licenses.py` changed a tracked file or left a new one |

Chatly only compiles on macOS, so everything that compiles Rust runs on the macOS runner. CI skips the `guard.rs` test, which needs a logged-in screen session, and doesn't run the end-to-end self-test, which needs a window and internet access. Run those yourself.

The last step catches two common misses: a new command whose `permissions/autogenerated/` file wasn't committed, and a dependency change without a regenerated `THIRD_PARTY_LICENSES.md`.

To run the same checks locally, install the tools once:

```bash
rustup component add rustfmt clippy
```

Then, in `src-tauri/`:

```bash

```

```bash
cargo clippy --locked --all-targets --all-features -- -D warnings
```

```bash
cargo test --locked --all-features
```

CI uses the latest stable Rust. A new Rust release can add Clippy warnings to code that passed before. Fix those in their own `chore:` pull request.

Third-party actions are pinned to a full commit SHA, because a tag can be moved to different code. The workflow has no comments, so the versions are listed here. Update this table when you change a pin:

## Branches, commits and pull requests

`main` is the stable development branch: everything on it has passed CI and review.

1. **Don't push to `main` directly.** Start every change on a branch from an up-to-date `main`:

   | Branch | For |
   |---|---|
   | `feature/<name>` | New features |
   | `fix/<name>` | Bug fixes |
   | `docs/<name>` | Documentation only |
   | `refactor/<name>` | Code changes that don't change behavior |
   | `security/<name>` | Hardening. For an unfixed vulnerability, report it privately first ([SECURITY.md](SECURITY.md)) rather than pushing a public branch. |

2. **Write commit messages as `<type>: <what changed>`**, in lower case and the imperative:

   | Type | Example |
   |---|---|
   | `feat` | `feat: add a setting to pause videos on switch` |
   | `fix` | `fix: keep focus on the lock screen after Touch ID is cancelled` |
   | `docs` | `docs: explain the cookie domain quirk` |
   | `refactor` | `refactor: split layout() into smaller functions` |
   | `test` | `test: cover lookalike domains in the allowlist` |
   | `security` | `security: refuse blob URLs from other origins` |
   | `chore` | `chore: update dependencies` |

3. **Open a pull request against `main`** and fill in the template, including the **Verify** step of the recipe you followed.
4. **CI must pass** before merging.
5. **Resolve every review conversation** before merging.
6. **Small contributions are squash-merged.** The pull request title becomes the commit on `main`, so write it in the same `<type>: …` form.

### Repository settings for maintainers

These rules are enforced in GitHub's settings, not by anything in this repository. Under **Settings → Rules → Rulesets**, add a branch ruleset for `main` with:

- **Restrict deletions** and **Block force pushes**.
- **Require a pull request before merging**, with **Require conversation resolution before merging**. Set required approvals to 1 once there are two maintainers. With a single maintainer, leave it at 0, since GitHub doesn't let you approve your own pull request.
- **Require status checks to pass**, with **Require branches to be up to date before merging**, and the checks `Format and syntax` and `Clippy, tests and build (macOS)`. They appear in the list after CI has run once.
- No bypass list, so the rules apply to administrators too.

Under **Settings → General → Pull Requests**, allow squash merging, and turn on **Automatically delete head branches**.

## Release builds

```bash
../scripts/build-release.sh
```

This builds `src-tauri/target/release/bundle/macos/Chatly.app` for the Mac it runs on. The script remaps your home folder to `~` in the binary's embedded file paths. It then checks the binary in every `Chatly.app` under `target/`, and fails if your home path is still in one of them. Delete old builds (`cargo clean`) if one from a plain build makes it fail. Never publish a binary built with a plain `cargo build` or `cargo tauri build`: those contain `/Users/<your-username>/…` hundreds of times.

Extra arguments go to `cargo tauri build`. To build one app for both Apple silicon and Intel, install both targets once:

```bash
rustup target add aarch64-apple-darwin x86_64-apple-darwin
```

```bash
../scripts/build-release.sh --target universal-apple-darwin
```

The app is then in `src-tauri/target/universal-apple-darwin/release/bundle/macos/`.

To release a new version, change it in **both** `src-tauri/Cargo.toml` and `src-tauri/tauri.conf.json`.

Builds are ad-hoc signed (`signingIdentity: "-"`) with the hardened runtime. **Developer ID signing and notarization aren't set up.** To set them up, set `signingIdentity` to your identity and follow [Tauri's macOS signing guide](https://v2.tauri.app/distribute/sign/macos/).

### Release checklist

Chatly has no published releases yet. Until Developer ID signing and notarization are set up, publish **source releases only**: a tag and release notes, with no app attached. An ad-hoc signed app is blocked by Gatekeeper on other Macs, and nobody can tell a genuine build from a modified one. Steps 7 to 10 only apply once signing is set up.

1. **Pick the version** using [Semantic Versioning](https://semver.org/). While Chatly is below 1.0, bump the minor version for new features or vault format changes, and the patch version for fixes.
2. **Bump it** in `src-tauri/Cargo.toml` and `src-tauri/tauri.conf.json`. Run `cargo build` so `Cargo.lock` picks up the new version, and commit all three files.
3. **Update `CHANGELOG.md`.** Rename "Unreleased" to `[<version>] - <YYYY-MM-DD>` and start a new empty "Unreleased" section above it.
4. **Run the tests** on a Mac, in `src-tauri/`: the [CI commands](#continuous-integration) including the `guard.rs` test, the [self-test](#end-to-end-self-test) with your vault moved aside, and the [manual checks](#manual-checks).
5. **Check dependencies**: `cargo audit`, then `python3 ../scripts/third_party_licenses.py` and review the diff ([Updating dependencies](#updating-dependencies)).
6. **Merge the release pull request** (`chore: release <version>`) once CI passes.
7. **Build** from the merged `main` with `../scripts/build-release.sh --target universal-apple-darwin`, with `signingIdentity` set to your Developer ID. Open the built app on Apple silicon and on Intel: set a password, sign in, lock, unlock, quit and reopen.
8. **Notarize and staple** the app as described in Tauri's guide. Then check it:

   ```bash
   codesign --verify --deep --strict --verbose=2 Chatly.app
   ```

   ```bash
   xcrun stapler validate Chatly.app
   ```

   ```bash
   spctl --assess --type execute --verbose Chatly.app
   ```

9. **Package it** without losing the signature:

   ```bash
   ditto -c -k --keepParent Chatly.app Chatly-<version>-macos-universal.zip
   ```

10. **Write SHA-256 checksums**:

    ```bash
    shasum -a 256 Chatly-<version>-macos-universal.zip > SHA256SUMS.txt
    ```

11. **Tag the release** on the merged commit and push the tag:

    ```bash
    git tag -a v<version> -m "Chatly <version>"
    ```

    ```bash
    git push origin v<version>
    ```

12. **Publish the GitHub Release** from the tag (**Releases → Draft a new release**). Use the version's `CHANGELOG.md` section as the notes. If you built an app, attach the zip, `SHA256SUMS.txt`, `LICENSE` and `THIRD_PARTY_LICENSES.md`.

## Code style

- The code has no comments, and neither do configuration files (TOML, YAML, JSON, shell, Python). When something is non-obvious, put the reasoning in this guide (usually under [Rules you must keep](#rules-you-must-keep)) or in your pull request description. Only the generated files in `permissions/autogenerated/` keep the header Tauri writes.
- Format Rust with `cargo fmt`. The rules (120-character lines) are in `src-tauri/rustfmt.toml`, and CI rejects unformatted code.
- Match the existing Rust style beyond what rustfmt does: early returns with `let … else`, small functions named for what they do.
- `cargo clippy --all-targets --all-features -- -D warnings` must pass. CI fails on any warning.
- User-facing text (errors, labels, dialogs) is short, plain and in sentence case: "Touch ID is turned off." not "Error: TouchID disabled!".
